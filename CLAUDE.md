# sinam-core

Le cerveau compilé unique de sinam — **complet depuis T5** : embeddings, stockage (schéma SQLite + sqlite-vec), classification + routing, decay, resummary/synthèse projet, digest hebdo, ressources web, sync P2P — écrit une fois en Rust et consommé partout : backend FastAPI Mac via PyO3, apps mobiles via UniFFI. Une seule implémentation, zéro divergence de logique entre plateformes. Repo public (Apache-2.0) : ne jamais y mettre d'URL Linear, de secrets ni de données utilisateur.

## Commands

```bash
cargo build                        # desktop (onnxruntime téléchargé au build, feature ort-download)
cargo test                         # tests unitaires ; SYNAPSE_MODEL_DIR=<dir> active les tests d'embedding
cargo run --example embed_cli -- <model_dir> [texte]   # smoke/parité on-device

# Wheel Python (host desktop) — TOUJOURS via maturin, jamais cargo build direct
cd crates/sinam-core-py && maturin build --release

# Android (l'app embarque libonnxruntime.so, ort le charge dynamiquement)
# Passer par le script : la voix demande cmake, le NDK et une archive vide.
./scripts/build-android.sh                         # ort-dynamic + voice
FEATURES=ort-dynamic ./scripts/build-android.sh    # sans le décodeur

# Binding Kotlin (UniFFI proc-macro : se génère depuis la lib compilée)
cargo build -p sinam-core-ffi
cargo run -p sinam-core-ffi --bin uniffi-bindgen -- generate \
  --library target/debug/libsinam_core_ffi.dylib --language kotlin --out-dir bindings/kotlin

# Parité vs Python prod (depuis le venv du backend synapse, wheel installée)
python tools/parity_check.py --model-dir ~/.synapse/models/paraphrase-multilingual-MiniLM-L12-v2-onnx-Q
python tools/gen_reference_vectors.py > reference_vectors.json   # golden vectors pour les tests on-device

# Transcription vocale (feature `voice` ; `voice-metal` sur Apple, GPU)
./scripts/fetch-whisper-model.sh                   # modèle ggml dans ~/.synapse/models/whisper
./scripts/fetch-whisper-model.sh silero-v5.1.2     # le détecteur de parole (1 Mo)
cargo test -p sinam-core --features voice          # l'amorçage se teste SANS la feature aussi
cargo run --release --features voice-metal --example voice_bench -- \
  --model ~/.synapse/models/whisper/ggml-large-v3-turbo-q5_0.bin \
  --corpus ~/.synapse/corpus-voix --db ~/.synapse/synapse.db --lang fr
```

## Module & refacti conventions

Workspace à 3 crates, avec une règle dure : **toute la logique vit dans `crates/sinam-core`, les bindings sont des wrappers sans cervelle** (conversion de types + mapping d'erreurs, rien d'autre). Si un binding a besoin d'un comportement, il se code dans le core.

- `crates/sinam-core` : lib pure Rust. Un module par domaine — `embedder.rs`, `storage.rs`/`schema.rs`/`migrate.rs` (T1), `sql.rs` (passerelle SQL des hôtes), `llm.rs` + `routing.rs` (T2, classif + routing), `sync.rs` (T3, HLC/LWW + `dedup_after_pull`), `decay.rs`/`summaries.rs`/`digest.rs`/`resources.rs` (T5), `snapshot.rs` (lecture locale : rend le même JSON que les endpoints de lecture de l'hôte — le SQL y est un miroir délibéré de `api/app.py` côté backend, faire évoluer les deux ensemble; couvre space+devices, les faits de projet, les files « À valider » tâches/liens et **toute la carte vivante** : communautés par **Louvain déterministe** (numérotation canonique, taille décroissante puis plus petit id — même règle côté backend), ressorts sémantiques kNN sur embeddings, et la **disposition** elle-même (portage de vis-network `forceAtlas2Based`). Le backend sert `GET /graph` depuis `read_graph` au lieu d'en garder une copie : une seule implémentation, donc la même carte en HTTP et hors ligne. Positions **non persistées**, le déterminisme du solveur remplace la persistance. Seuls les libellés de zone restent à l'hôte, c'est un appel LLM), `actions.rs` (écritures locales : `apply_action` = 33 actions miroir des endpoints d'écriture du backend, même règle de miroir que snapshot.rs; rejeux caducs = statuts `not_found`/`skipped`, jamais d'erreur bloquante pour la file de l'app). `pairing.rs` couvre aussi le canal code 6 chiffres (SPAKE2 symétrique + MAC de confirmation `code_confirm_mac/verify`; un code court dans le HKDF serait brute-forçable hors ligne — jamais ça); `seal`/`open` prennent les messages de handshake en slices (clés X25519 32 o ou messages SPAKE2 33 o). `lib.rs` reste un point d'entrée mince qui ré-exporte.
- `transcribe.rs` : transcription vocale locale, coupée en deux à dessein. L'**amorçage par le graphe** (`graph_names`, `graph_prompt`, exposés aux hôtes par `SqlConnection::voice_names` / `voice_prompt`) est du SQL et du texte : il compile et se teste TOUJOURS, feature ou non, et c'est la seule moitié qui porte une décision produit. Le décodeur whisper.cpp (`Transcriber`, feature `voice`) n'est qu'une liaison. Ce que l'amorçage attaque : une faute sur un nom propre ne produit pas une faute visible que l'utilisateur corrige, elle produit une **entité en double**, en silence. Les noms injectés sont classés `memory_strength` d'abord (elle porte déjà « souvent ET récemment »), noms propres devant, entités archivées / fusionnées / en attente exclues. « Nom propre » se décide par la capitale initiale **ou** par le type, jamais par le type seul : le vocabulaire des types est extensible par l'usage (`brand`, `device`, `restaurant` sont apparus après coup), donc une liste figée reléguerait au second rideau exactement les noms que le décodeur écorche. Le budget est de 180 tokens : whisper.cpp n'en garde que `n_text_ctx / 2` = 224 et tronque par la FIN, donc relever ce budget obligerait à émettre les noms les plus forts en dernier. Contre l'hallucination sur le silence, **deux mécanismes mesurés, et deux culs-de-sac à ne pas reprendre** : `no_speech_prob` vaut **0 partout** sur les modèles publiés (base, small, large-v3-turbo quantifiés), y compris sur du souffle de pièce sans un mot, et la logprob ne sépare pas non plus (souffle -0,305 contre parole -0,258, plages recouvrantes) ; une règle bâtie sur ces deux nombres est INERTE, et pire qu'absente puisqu'elle rassure. Ce qui marche : le **détecteur de parole** (silero, 1 Mo) en amont, et la **forme du texte** (`*soupir*`, `[Musique]`, `...` ne sont pas de la parole). Mesuré : le VAD ne change rien aux noms retrouvés et fait gagner 30 % de temps de décodage, puisque le silence n'est plus décodé. Un segment écarté lève `needs_review`, il n'est jamais effacé ; quand le détecteur ne trouve aucune parole, `speech_detected` est faux et l'hôte n'écrit RIEN.
- **Le brut ne se perd pas** : `inbox.raw_content` garde le texte tel qu'il est arrivé quand ce qui a été gardé n'est pas lui (sortie de transcription, frappe avant autocorrection). NULL veut dire « `content` EST le brut », donc toutes les lignes antérieures restent vraies. Un correcteur se trompe là où ça coûte le plus cher (noms propres, acronymes, jargon, formulations volontaires) et, contrairement à une mauvaise note, il n'y a rien derrière pour rattraper si la source est écrasée.
- **Quatre décisions d'identité ne s'appliquent JAMAIS à la capture** — type d'entité, fusion d'entités, fusion de prédicats, renommage d'entité. Elles s'écrivent en propositions (`*_proposals`, toutes répliquées) et un humain tranche. L'invariant n'est pas « le modèle se trompe parfois » mais **ce que l'erreur coûte** : chacune change l'IDENTITÉ de quelque chose que l'utilisateur lit comme étant sa mémoire, et une identité changée à tort ne se remarque pas. La négation d'un fait est le seul cas qui peut s'appliquer tout de suite, et c'est la même règle appliquée : périmer est RÉVERSIBLE (`obsoleted_at`, annulé par `/fact/{id}/restore`). Quand sa cible n'est pas certaine, elle retourne en file comme les autres.
- **Deux mécanismes mesurés à ne pas réessayer** : embedder le NOM d'un prédicat ne sépare pas les synonymes des inverses (`parent_of` ⇄ `child_of` sortent plus haut que `works_as` ⇄ `works_at`), d'où la restriction de la passe de réconciliation aux seules familles mono-valuées ; et la signature lexicale a un faux positif connu sur données réelles (`worked_at` vs `works_at` sur la même personne = ancien et actuel employeur, pas deux noms d'une affirmation). Les deux étages proposent, aucun n'applique — et ça condamne l'idée de les automatiser un jour.
- **Règle transactionnelle** : ce qui doit s'exécuter dans la transaction du caller s'expose sur `SqlConnection` (insert_fact, decay, gather_week, add_project_entry, read_snapshot) ; les passes LLM/vecteurs vivent sur `Brain` (sa propre connexion) et s'appellent hors transaction hôte — sinon SQLITE_BUSY.
- **Prompts** : `prompts/*.md` + `manifest.json`, byte-identiques aux constantes Python historiques (`llm::load_prompt` strippe le `\n` final). Déployés côté hôtes dans `~/.synapse/prompts/` — les livrer avant/avec toute wheel qui les lit. ⚠️ **Un prompt est de la donnée recopiée sur CHAQUE surface** : `~/.synapse/prompts/` (Mac dev + Mac mini prod), assets de l'app Android/iOS, backend bundlé du `.dmg`/Windows. Le changer ici ne le livre **nulle part**.
- **Classifieur = DEUX appels** : `classifier-note.md` (routage + prose) et `classifier-graph.md` (entités, faits, relations, projets), fusionnés par `llm::merge_halves`. `classifier.md` reste comme repli documenté et référence de taille, **plus lu par le core**. Le découpage rend l'invariant « la note n'est jamais absorbée » **structurel** : l'appel graphe n'a pas de champ `memories`, il ne peut pas le vider — la règle disparaît du prompt au lieu d'y être répétée quatre fois. Deux effets de bord mesurés, à connaître avant de retoucher une moitié : (1) séparée de la note, la moitié graphe **sur-extrait** si rien ne l'en empêche (19 → 43 faits ; d'où la règle de sobriété en tête de `classifier-graph.md`, qui distingue la liberté de ne pas s'auto-censurer du volume) ; (2) **Haiku ne cache un préfixe système qu'au-dessus de 4096 tokens.** C'est une falaise, pas une pente : grossir une moitié au-delà du seuil coûte MOINS cher que la laisser juste en dessous.

  ⚠️ **Le point (2) s'est inversé, et cette ligne disait le contraire jusqu'au 2026-09-01.** Au découpage, les deux moitiés étaient tombées sous le plancher (~2900 et ~2400) et le surcoût était assumé. Elles ont grossi depuis, règle après règle : **~5150 et ~4660 tokens** aujourd'hui, donc **les deux sont cachées à nouveau**. La passe complète du 01/09 le mesure sans ambiguïté : 164 k tokens d'entrée facturés contre **5 098 k relus du cache**. Conséquence pratique : la taille du prompt ne se paie plus à chaque capture, c'est la SORTIE qui porte le coût. Ne pas raisonner sur l'ancienne ligne pour justifier une compaction.
- **Trois champs de sortie dont l'ABSENCE doit être sûre** : `obsoleted_facts`, `renamed_to`, et le `type_proposal` historique. `merge_halves` force les tableaux à exister, et le mode d'échec est délibéré : si le modèle oublie le champ, il ne se passe RIEN. C'est pourquoi la négation est un tableau à part et pas un drapeau `negated` sur le fait — un drapeau oublié écrit l'exact contraire de ce que dit la capture. L'inaction, jamais l'inversion.
- **Multilingue (FR/EN-first, extensible)** : les prompts sont **EN-base neutre**, la sortie suit la langue de la capture; prédicats/types restent EN snake_case (interlingua). Le classifieur émet un champ `"language"` (ISO 639-1) — **détection 100% côté serveur, dans le prompt** (zéro dépendance/appel en plus). Stocké en `atomic_notes.language` (lu du JSON dans `routing.rs::persist_atomic_note`). Les résumés d'entité ne peuvent PAS inférer la langue (faits/relations = prédicats EN + noms propres) → `summaries.rs::dominant_note_language` fait un **vote majoritaire déterministe** sur `atomic_notes.language`, injecté via `{language}` dans `resummary.md`. Digest/resource-summary infèrent bien (vraie prose en entrée). Garde-fou = harness Haiku côté repo `synapse` (`scripts/lang_harness.py`), 0 régression FR. Ajouter une langue = 0 travail cœur.
- `crates/sinam-core-py` : PyO3, module Python `sinam_core` (le crate/fn s'appelle `sinam_core_py` pour éviter la collision de noms avec la dépendance). Exclu des `default-members` : build via **maturin uniquement** (link `-undefined dynamic_lookup`). Libérer le GIL (`py.detach`) autour de tout appel coûteux.
- `crates/sinam-core-ffi` : UniFFI proc-macro (`uniffi::setup_scaffolding!`). Sorties générées dans `bindings/` (gitignoré, régénérable).
- **Les fichiers modèle et les prompts sont de la donnée, jamais du code** : passés en chemin au runtime, bundlés en assets côté apps, jamais commités (App Store 2.5.2). Le comportement (ex. troncature) se lit depuis les fichiers modèle, pas de constantes en dur qui divergeraient de Python.
- Features : `ort-download` (défaut, desktop) vs `ort-dynamic` (mobile, l'app fournit libonnxruntime). Tout nouveau code doit compiler sous les deux. `voice` (whisper.cpp) et `voice-metal` (Apple, GPU) sont hors du défaut : elles n'ajoutent qu'un décodeur, et la partie du module vocal qui décide de quelque chose compile sans elles.
- Cleanup structurel = commit dédié, jamais mélangé à une feature.

### Pièges verrouillés (ne pas re-payer)

- **Matrice de versions** : fastembed 5.17 → ort `=2.0.0-rc.12` (api-24) → onnxruntime ≥ 1.24 (AAR Android `1.27.0`). Un onnxruntime trop vieux ne donne pas d'erreur : ort rc.12 **deadlocke** (OnceLock réentrant dans son chemin d'erreur). Ne bumper fastembed/ort qu'ensemble, en revérifiant la matrice.
- **Croiser whisper.cpp vers Android demande trois choses, et aucune ne se signale clairement** (toutes tenues par `scripts/build-android.sh`) : le cmake du SDK Android avec son ninja (les Command Line Tools n'en fournissent pas) ; `scripts/android-toolchain.cmake`, qui pose l'ABI **avant** d'inclure celle du NDK (celle du NDK lit `ANDROID_ABI` comme variable cmake, jamais comme variable d'environnement, et le crate `cmake` ne sait pas passer de `-D` : sans ça elle retombe sur armeabi-v7a et casse sur « unsupported argument 'armv7-a' ») ; et une archive `libggml-blas.a` **vide**, parce que whisper-rs-sys teste `cfg!(target_os = "macos")` DANS son build script, donc sur l'HÔTE, et réclame en croisant une bibliothèque que la compilation Android ne produit pas. Au passage : `RUSTFLAGS` se découpe sur les espaces et le chemin du dépôt en contient un, d'où `CARGO_ENCODED_RUSTFLAGS`.
- **Trois réglages font la vitesse sur téléphone, et deux ne se voient pas** (mesuré sur Pixel 9a) : (1) `-march=armv8.2-a+dotprod+i8mm+fp16` dans la chaîne d'outils, sans quoi les noyaux quantifiés de ggml prennent le chemin lent alors que `/proc/cpuinfo` annonce `asimddp` et `i8mm` ; (2) `set_audio_ctx` ramené à la durée réelle, parce que whisper encode TOUJOURS 30 s et paie le silence de bourrage plein pot sur une capture courte ; (3) **3 fils** : mesuré deux fois, 6,1 s à trois contre 7,8 s à quatre et 6,5 s à deux sur la même capture ; au-delà le planificateur part sur les cœurs d'efficacité. ⚠️ **Ne PAS couper `temperature_inc` pour borner la latence, ça a été fait et c'était un bug.** Le repli en température est le SEUL mécanisme qui sort whisper d'une boucle de répétition ; sans lui un segment parti en vrille (« oaia oaia oaia ») est rendu tel quel dans la note. Le piège est que le banc donne raison à qui le coupe : il ne se déclenche jamais sur un corpus propre, précisément parce qu'il ne sert que sur les cas qu'un corpus ne contient pas. Observé en usage réel, jamais au banc, et remesuré gratuit sur une capture saine (0,61 s contre 0,63 s).
- **⚠️ La marge de `set_audio_ctx` n'est PAS gratuite, contrairement à ce que cette ligne a dit jusqu'au 2026-09-02.** Le réglage (2) ci-dessus a un palier net, mesuré sur trente captures réelles avec `small` : marge de **+128** trames = 22,4 % de taux d'erreur mot, marge de **+300** = 18,0 %, c'est-à-dire **exactement** la qualité de la fenêtre pleine, pour 0,7× le temps réel au lieu de 1,4×. Entre les deux valeurs il n'y a rien à grappiller, et rogner la marge pour gagner une seconde reprend les quatre points d'un coup. La formule est `+300`, plancher 600.
- **Le modèle mobile est `small`, et l'arbitrage vitesse/qualité qu'on croyait payer n'existe pas.** Une fois la marge de fenêtre correcte, small décode à 0,7× le temps réel sur un Pixel 9a, soit la vitesse de base ; le « small à 2,4× » qui avait fait descendre à base était une mesure fausse. L'écart de qualité, lui, est énorme et porte sur le français ordinaire, pas seulement sur les noms propres : **21,8 % de taux d'erreur mot contre 33,7 %** par le chemin exact de l'app (tranches de 6 s), base rendant « pan de marre » pour « pain demain ». Et ce n'est pas la compression : `base-q8_0` fait 30,5 % et `base` en f16 29,7 %, c'est la taille du modèle qui manque. Sur desktop la question ne se pose pas, Metal met small à 0,25×.
- **Transcrire par tranches coûte 3,8 points** (21,8 % contre 18,0 % sur le fichier entier) parce qu'une tranche perd le contexte de la précédente, et c'est le prix assumé de voir le texte arriver pendant qu'on parle. ⚠️ **Reporter les derniers mots de la tranche précédente dans l'amorçage ne le répare pas, il l'aggrave** : 24,4 %, mesuré à douze et à vingt-quatre mots reportés — le report chasse les noms du budget de 224 tokens. L'amorçage par les noms, lui, ne coûte rien au reste du texte : 18,0 % avec comme sans.
- **⚠️ `language: None` (détection automatique) coûte 8 à 10 secondes par capture sur téléphone.** Mesuré sur un Pixel 9a, même clip de 6 s : 5,4 s avec la langue fixée, 13 à 15 s en détection. Le surcoût est **FIXE** et non proportionnel (+1,2 s sur Mac que le clip fasse 3, 6 ou 12 s) parce que la passe de détection encode la fenêtre de 30 s **entière**, sans tenir compte de `set_audio_ctx`. Il ne s'amortit donc pas sur une capture courte, il la triple. Un hôte doit passer une langue : celle de l'appareil à défaut, jamais la détection par commodité. Corollaire produit : un sélecteur de langue à l'écran n'est pas une verrue d'interface, il vaut huit secondes par capture.
- **Quatre pistes de latence mesurées et mortes** (ne pas les rouvrir sans raison neuve) : `flash_attn` rend le décodage **45 % plus lent** sur processeur pour un texte identique (le gain qu'on lui prête vient des GPU de datacenter) ; passer de `q5_1` à `q8_0` ne change ni la vitesse ni la qualité et coûte 71 Mo de plus ; l'amorçage par les noms ne coûte **rien** en temps (0,60 s contre 0,62 s) donc le raccourcir ne rachète pas de latence ; et les instructions ARM sont bien dans le `.so` (646 `sdot`, 196 `smmla` vérifiés à l'objdump), il n'y a rien à récupérer côté compilation.
- **L'échelle des modèles est monotone, il n'y a pas de bon coup à jouer** (même prise de 191 s, même amorçage) : tiny 32,3 % de taux d'erreur mot, base 25,6 %, small 13,7 %, large-v3-turbo 10,2 %. Et le coût suit : sur processeur, pour un clip de 6 s, base 0,24 s, small 0,77 s, large-v3-turbo 2,25 s. `small` n'est pas un compromis malin, c'est **le plus gros qui tient dans le budget de temps d'un téléphone**.
- **Le vrai streaming ne se fait PAS en découpant.** Ce qui rend une transcription au fil de l'eau sans perte, c'est de redécoder des fenêtres qui se recouvrent et de ne figer que ce sur quoi deux passes s'accordent, donc de décoder chaque seconde d'audio deux ou trois fois. Le Pixel 9a décode à 0,7× le temps réel avec small : il reste 1,4× de marge là où il en faudrait 3. Découper en morceaux disjoints est la version pauvre, et c'est elle qui coûte les points (27,9 % contre 13,7 %).
- **iOS décode par le GPU, Android par le processeur, et ce n'est pas une asymétrie subie.** whisper.cpp sait utiliser Metal sur iOS (`voice-metal` dans `ios.yml`), là où le Mali d'un Pixel lui est inaccessible sans un chantier Vulkan. Mesuré sur M1 : Metal met `small` à 0,25× le temps réel contre 0,13× au processeur, et rend `large-v3-turbo` jouable. Conséquence produit : **le modèle par défaut se décide par appareil, pas par symétrie** — `small` sur Android (0,7× le temps réel sur un Pixel 9a, turbo y serait à 2×), potentiellement turbo sur iPhone et déjà turbo sur desktop. L'app iOS doit lier **Metal et MetalKit** en plus d'Accelerate, et `libggml-metal.a` entre dans les archives fusionnées.
- **Croiser whisper.cpp vers iOS passe, mais l'archive statique est un piège de plus.** Contrairement à Android, aucun réglage de chaîne d'outils n'est nécessaire (cmake+Xcode s'en sortent seuls, et `libggml-blas.a` existe parce que ggml active Accelerate par défaut sur Apple — **l'app doit donc lier `Accelerate.framework`**). En revanche cmake pose whisper et ggml en archives **séparées** dans le `OUT_DIR` du build script : sur Android le cdylib les absorbe, sur iOS on produit une bibliothèque STATIQUE et elles ne sont embarquées nulle part. Le xcframework part alors sans elles et c'est l'**app** qui échoue à l'édition de liens, sur des symboles `whisper_*` introuvables, très loin de la cause. `.github/workflows/ios.yml` les fusionne par `libtool -static` avant de créer le xcframework.
- **Le binding Kotlin doit être généré avec les MÊMES features** que la lib Android depuis que le décodeur existe : sorti d'un build hôte sans `voice`, il n'a pas de `Transcriber` et l'app ne compile pas.
- **L'audio traverse la FFI en OCTETS**, jamais en `Vec<i16>` : UniFFI rend un tableau de shorts sous forme de liste d'objets, soit 320 000 allocations pour vingt secondes de parole, là où un tableau d'octets passe tel quel. C'est aussi ce que rend `AudioRecord.read(byte[])`.
- **Le VAD de whisper.cpp ne s'applique QUE dans `whisper_full()`**, jamais dans `whisper_full_with_state()`, par lequel passe toute liaison qui gère son propre état (donc whisper-rs, donc nous). Poser `vad_model_path` + `enable_vad(true)` ne produit alors **aucun effet et aucune erreur**, pas même avec un chemin de modèle inexistant : le filtrage est refait à la main dans `transcribe::speech_only`. Ne pas « simplifier » en rendant la main au drapeau.
- **`ORT_DYLIB_PATH` ne doit jamais pointer vers un chemin inexistant** (même deadlock). Sur Android (`extractNativeLibs=false`), les .so ne sont pas extraits sur disque : précharger via `System.loadLibrary("onnxruntime")` et laisser ort dlopen par soname.
- Troncature embeddings : le modèle qdrant tronque à **128 tokens** (min de `max_length`/`model_max_length` dans `tokenizer_config.json`, comme fastembed Python) — et 128 est le BON granule pour ce modèle de phrases : embedder un texte long en un seul vecteur 512 **dilue** (mesuré : les requêtes tête ET queue chutent). Les textes longs sont **chunkés** : `Embedder::embed_chunks` = un vecteur par fenêtre de ~128 tokens (overlap 24, max 16 fenêtres) ; notes = une ligne vec0 par chunk (clé `uuid` puis `uuid#k`, `search_notes` déduplique au meilleur chunk) ; ressources = frames concaténées dans le BLOB (`score_against_frames` = max). vec0 ne supporte pas INSERT OR REPLACE : l'upsert balaie puis insère.
- `intra_threads(1)` sur mobile.
- **whisper.cpp se construit par cmake**, que les Command Line Tools d'Apple ne fournissent pas. Sur une machine sans gestionnaire de paquets, le SDK Android en embarque un utilisable : le mettre dans le PATH suffit (chemin exact dans `CLAUDE.local.md`, il est propre à la machine).
- **Le processeur seul ne suit pas** pour la transcription : mesuré sur M1, un clip de 4 s en `large-v3-turbo-q5` prend environ 8 s en `voice` nu (et monter les threads à 8 empire les choses, ce sont des cœurs d'efficacité) contre environ 3 s en `voice-metal`. Une boucle de capture desktop passe par Metal ; le mobile devra descendre de modèle, pas de threads.

## Tests

- Framework : `cargo test` (tests unitaires dans les modules). Les tests nécessitant le modèle lisent `SYNAPSE_MODEL_DIR` et se **skippent** (pas d'échec) s'il est absent : la suite reste exécutable offline et sans les 235 Mo de modèle.
- **Règle stricte : aucune feature ne ship sans test.** Pour tout ce qui touche la parité avec Python (embeddings, et bientôt stockage/routing), le test de référence est un **golden test** : vecteurs/sorties générés côté Python prod (`tools/gen_reference_vectors.py`), comparés côté Rust (seuils : cosinus > 0.9999, cf. `tools/parity_check.py`). C'est le contrat du repo.
- Validation on-device : `examples/embed_cli.rs` (CLI + mode parité + watchdog SIGUSR1) pour Android via adb ; le test instrumenté complet vit dans `synapse-app` (`EmbedderParityTest`).
- Lancer `cargo test` (les deux features si le build system est touché) avant tout commit.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

## Environment

Pas de `.env`. Variables utiles :
- `SYNAPSE_MODEL_DIR` : dossier des fichiers modèle (ex. `~/.synapse/models/paraphrase-multilingual-MiniLM-L12-v2-onnx-Q`) ; active les tests d'embedding.
- Modèle whisper : aucun défaut, il se passe en `--model` (fichier ggml, donnée jamais commitée). `./scripts/fetch-whisper-model.sh` le dépose dans `~/.synapse/models/whisper/`.
- Corpus vocal de mesure : hors du dépôt (données personnelles), voir `docs/voix-corpus-protocole.md`.
- `ORT_DYLIB_PATH` : chemin explicite vers libonnxruntime pour les builds `ort-dynamic` (CLI on-device). Ne jamais le définir vers un chemin inexistant, et ne pas le définir dans une app Android.
